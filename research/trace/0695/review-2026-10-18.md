# Code review: client-0.695, changes since 2026-10-17 12:00

Read-only review of `git diff 01ca449..HEAD` on `client-0.695` in `<workspace>\LandmarkEmu`. That is the first-parent base before
`322d6eb` (2026-10-17 12:21). HEAD is `e5e72fe`. It includes `38f752b` (channelled sprint), which landed while this review
was running. The diff covers 213 files, +15 322 / −2 296 lines.

The review looks for real defects only: thread safety, crashes, unbounded growth, double application, units, wire layouts,
Docker wiring, migrations, and regressions in other systems. Line numbers are at HEAD `e5e72fe`.

**Threading model.** Game code runs on the single world thread (`ThreadManager` → `HostedService` tick). The gateway
link, the commerce link and the web pages queue their work onto that thread. So the real thread hazards are:
- `Task.Run` / `Task.Delay(...).ContinueWith` callbacks, which run on pool threads;
- the web-page handlers that do not go through `OnWorldThread`;
- the commerce/link reader threads.

The dictionaries added today for HeroicMovement swimmers, TeleportRequests, WeaponCombat sweeps and Props.Platforms are
locked and are touched from the world thread. No defect was found in them.

## Ranked findings

### 1. HIGH: Player Studio creator shares can be mailed more than once (Lumens created from nothing)

- **Where:**
  - `LandmarkEmulator.CommerceServer/CommerceHub.cs:320` (`Products.SendPendingPayouts(world)` in `Hello`)
  - `LandmarkEmulator.CommerceServer/ProductService.cs:494-498` (`SendPendingPayouts`)
  - `LandmarkEmulator.WorldServer/Game/WorldChannel/RemoteCommerceService.cs:290-296` (`case CommercePayout`)
- **Failure:** Every world that links (sends `CommerceHello`) gets **every** pending `studio_payout` row of its realm. There
  is no record of which world was already given which payout. The world side mails the share with Lumens attached
  (`Commerce.MailCreatorShare`), then confirms. It does not deduplicate.
  - **Scenario A (service restart):** The commerce service restarts with two worlds in the realm, which is the normal setup
    since the worlds share the character database. Both worlds re-hello within seconds. Each one mails every
    unconfirmed share, so the creator receives it twice.
  - **Scenario B (one world):** A world mailed a share, but its `CommercePayoutSent` was lost because the link dropped
    before the send. On reconnect the share is mailed again.
  - Each duplicate is real currency.
- **Fix:**
  1. Give payouts the same in-flight guard as `FollowService.SendPending` (`inFlight[payout.Id] = (world, now)`). Skip a
     payout that another world with an open link was given less than N minutes ago.
  2. Make the world side idempotent. Before mailing, record the payout id (for example `Unlocks.Add(creator, PayoutKind,
     payoutId)`, or a small `commerce_payout_done` table in the character DB). If the id is already present, confirm
     without mailing.
  - Fix 2 also closes the lost-confirmation case, which fix 1 alone cannot.
  - The digest mails (`FollowService` / `DeliverDigest`) have the same at-least-once delivery. A duplicate there is
    harmless text, so it is acceptable.

### 2. MEDIUM-HIGH: a hold timer re-enters a disconnected session into the world (ghost player, double Leave, can kick a fresh login)

- **Where:**
  - `LandmarkEmulator.WorldServer/Game/Teleport.cs:216` (`Teleport.Update`: `if (PlayerManager.Snapshot().Contains(a.Session) || a.Session.WorldReady)`)
  - `LandmarkEmulator.WorldServer/Network/Handlers/MiscHandler.cs:243` (`FinishZoneIn`: `if (session.WorldReady && !Snapshot().Contains(session)) PlayerManager.Enter(session)`)
  - Scheduled at `MiscHandler.cs:275` (Spire, 6 s) and `:287` (props, 4 s).
- **Failure:**
  - `WorldReady` is set at ClientFinishedLoading and **never cleared**. The comment on `After` says it is "dropped if the
    player left meanwhile", but that is not true.
  - The player can disconnect during the 4 s or 6 s arrival hold. This is the moment players crash or Alt-F4 after falling
    through the deck. `LinkClosed` → `PlayerManager.Leave` runs, and then the timer fires. `FinishZoneIn` calls
    `PlayerManager.Enter` on the dead session.
  - That call adds the session back to `players`, introduces it to everyone, and runs `Social.PlayerEntered`. Friends see
    the player come online.
  - Within one second `PruneDead` runs `Leave` a second time: offline notices again, `EncounterLeave` again, and so on.
  - If the same character has already logged in again in that window, `Enter`'s stale-session block calls `Leave(newSession)`
    and **kicks the new client** with "Your character has logged in from another location". A relogin key ("R…") makes
    a fast relog plausible.
  - Before today `FinishZoneIn` ran synchronously in the ClientIsReady handler, so this is a regression.
- **Fix:**
  - In `Teleport.Update`, change the guard to `if (!a.Session.Disconnected && (Snapshot().Contains(a.Session) || a.Session.WorldReady))`.
  - Add `if (session.Disconnected) return;` at the top of `FinishZoneIn`.
  - Optionally, have `PlayerManager.Enter` refuse `session.Disconnected`.

### 3. MEDIUM: the arrival hold is not tied to its re-zone (zone-done flags can arrive mid-load; moves during the hold are swallowed)

- **Where:**
  - `MiscHandler.cs:271-288` (the `Teleport.After(..., () => FinishZoneIn(session))` holds)
  - `Teleport.cs:184-190` (`Rezone`: same landscape → retarget only; another landscape → `RezoneNow` even though one is
    pending)
  - `Teleport.cs:292` (`FinishRezone` only clears the target)
  - `PlayerManager.cs:189-198` (`PropsSentEarly` / `SpireSentEarly` consumed by whichever `Reintroduce` runs next)
- **Failure:** During the 4 s or 6 s hold `RezoneTarget` is still set, so the player is "re-zoning". Three things can go
  wrong:
  - **(a) A cross-landscape re-zone during the hold.** Examples: a Game Finder arrival, a site-game spawn, a GM move, grief
    or encounter handling. It sends a second ClientBeginZoning at once. The first hold's timer then fires during the second
    load and sends `DoneSendingPreloadCharacters` + `ZoneDoneSendingInitialData` + `Reintroduce` + `FinishRezone` before
    the second ClientIsReady. This is the "anything sent during a re-zone can hang the client" case from
    docs/terrain.md and the cave-teleport-hang memory.
    - `FinishRezone` also clears `RezoneTarget` early, so the next move is no longer held.
    - When the second ClientIsReady comes, everything is sent again.
    - If the second arrival is not over props, its `Reintroduce` still sees `PropsSentEarly == true` from the first. It
      skips `Props.SendAll` for the **new** landscape until the old timer happens to run `Reintroduce` again.
  - **(b) A same-landscape move during the hold.** Examples: an evac answer, a Translocation Pad, `InstancedGames` spawn
    `Teleport.To`. It only calls `SetPosition` and retargets. `FinishRezone` never moves the client there, so server and
    client positions disagree.
    - This existed before. The hold widens the window from about 0 s to 4-6 s.
  - **(c) A Play/Edit toggle during a props hold.** `Props.PlayModeVisibilityChanged` skips players with `RezoneTarget != null`
    (Props.PlayModeVisibility.cs:103). That relies on `SendAll` at the arrival, but with `PropsSentEarly` the `SendAll`
    already ran before the hold. The story-tool visibility is left stale.
- **Fix:**
  - Give each re-zone a generation number. Add `session.RezoneSerial++` in `RezoneNow` and capture it when the hold is
    scheduled. In the callback, `if (session.RezoneSerial != serial) return;`.
  - Clear `PropsSentEarly` / `SpireSentEarly` in `RezoneNow`.
  - In `Rezone`, defer a cross-landscape re-zone while `RezoneTarget != null`, for example in the `deferred` map with
    `Due = now + 0.5 s`. This makes "one zone change at a time" hold across landscapes too.
  - In `FinishRezone`, if the retargeted position differs from where the client was zoned to, send the plain
    `TeleportToLocation` there. A same-landscape short move is safe after ClientIsReady.

### 4. MEDIUM: listing-fee refunds are matched FIFO and by timeout, not by request, so listings can be free or fees kept

- **Where:** `RemoteCommerceService.cs:547-575` (`WatchCreateResponse`) and `:580-610` (`ExpireCreates`).
- **Failure:** The fee is taken in the world. It is settled by the *next* 0x31 CreateResponse the service tunnels to that
  `WorldSession`, or refunded after 30 s or on link loss.
  - **(a) Late or lost answer.** The service stores and lists the product (status 1), but its answer is late (more than
    30 s under DB load), lost because the link dropped after the commit, or dropped by `Deliver` because the player
    reconnected under a new connection id. The fee is refunded anyway, so the design is listed for free. Only a log Warn
    records it (line 564).
  - **(b) Player disconnected.** The fee is "kept" (line 600) even when the service refused the create. The refusal goes
    to the old connection and nothing ever settles it.
- **Fix:**
  - Put a create id in `CommerceProductCreate`, for example the `RequestId` that `Ask` already uses for other requests.
  - Have the service answer with a typed `CommerceProductCreateResult {RequestId, Status}` next to the tunnelled client
    packet.
  - Settle by id, and only refund on an explicit non-1 status or on a service-confirmed "not stored" answer. When the link
    is lost, query the product by (owner, item id) at the next hello instead of refunding blindly.

### 5. MEDIUM-LOW: digest runs are marked done before their work, so a failure loses a day or a window of mails

- **Where:**
  - `LandmarkEmulator.WorldServer/Game/ShowcaseFollow.cs:311-315` (`finally { doneDay = day; ... }`)
  - `ShowcaseFollow.cs:346-358` (run row saved before `Compose`)
  - `LandmarkEmulator.CommerceServer/FollowService.cs:164-176` (`AddDigestRun` before `Compose`)
- **Failure:**
  - **In-process, failure before the run row.** A transient DB error before the run row is written still sets `doneDay`
    in the `finally`, so the day's digest is skipped entirely until tomorrow.
  - **In-process, failure after the run row.** A failure after the row is written (in `Compose` / `GetCharacterNames`)
    leaves a run whose `RanAt` becomes the next run's `since`. The items listed in that window are never mailed.
  - **Service.** `Tick`'s comment says "tried again next minute", but the slot is already recorded, so the realm is
    "already run" for the day and that window's mails are lost the same way.
  - **Server stop.** A shutdown while the in-process `outbox` still holds letters loses them, because the run is
    recorded.
- **Fix:**
  - Set `doneDay` only on success.
  - Record the run row with a `Mails = uint.MaxValue` or `pending` marker. Set the final count only after `Compose` and the
    enqueue succeed.
  - Have the next run take `since` from the newest *completed* run, not the newest row.
  - In-process: persist letters (or the run's window) before marking the run completed, as the service already does with
    `digest_mail`.

### 6. MEDIUM-LOW: MovementEffects runs game logic on pool threads (`Task.Delay(...).ContinueWith`)

- **Where:** `LandmarkEmulator.WorldServer/Game/MovementEffects.cs`:
  - `:369` (charge timeout → `End` → `Finish`)
  - `:480-525` (`ScheduleTick` / `Tick`: `Health.IsDead`, `WeaponAttacks.TrySpendEnergy` → `EnergyCap` → `Combat.Gear.Has`
    enumerating `session.Inventory.Items`, `EndChannel` → `StartCooldown`, `Abilities.SendAbilityEnd`)
  - `:576` (release answer)
- **Failure:**
  - `Tick` reads session state that the world thread mutates. `Gear.Has` iterates the inventory while the world thread
    adds gathered items (sprinting while harvesting), which can throw "Collection was modified".
  - Any exception in the continuation is swallowed: the task faults unobserved and no further `ScheduleTick` happens. The
    channel then never drains Energy and never ends server-side (no CastSuccess on death or zone change) until the player
    releases the key.
  - **TOCTOU in `End` (`:399-404`):** it checks under the lock, releases it, then calls `Finish(p, null)`, which removes
    *whatever* charge is current. A leap started in between gets a premature CastSuccess, which ends its charge.
- **Fix:**
  - Run these timers on the world tick, as `WeaponCombat.Later` and `Teleport.After` do. For example, add
    `MovementEffects.Update()` to `HostedService` and keep `(due, action)` lists, or call `Teleport.After(p, ms, ...)`.
  - In `End`, remove the entry inside the same lock and call the answer outside it, instead of calling `Finish`.

### 7. LOW-MEDIUM: Grief state and other forgets are skipped for sessions that never entered the world

- **Where:**
  - `LandmarkEmulator.WorldServer/Game/PlayerManager.cs:246` (`if (!players.Remove(session)) return;` returns from `Leave`
    entirely)
  - `Game/Grief.cs:148` (`SelfData` puts a `State` into `states` at SendSelf)
- **Failure:**
  - A client that receives SendSelf and disconnects before `PlayerManager.Enter` never reaches `Grief.Leave` or the other
    post-lock forgets (`Groups`, `Pets`, `Telemetry`, `WarpNetwork`, …). Examples: a crash during loading, or a grief-
    suspended character turned away early.
  - Each aborted login leaks one `Grief.State`, which `Grief.Update` walks every second forever. Its `Session` reference
    also keeps the whole `WorldSession` and its buffers alive.
  - Small per event, but it is unbounded on a public server with flaky clients.
- **Fix:**
  - Make `Grief.Leave` (and the other new per-session forgets) run even when the session wasn't in `players`. For example,
    move the early `return` to cover only the "remove from others' view" part.
  - Alternatively, have `Grief.Update` drop states whose `Session.Disconnected` is true after saving them.

### 8. LOW: in-process follow / AccountStore now do database round-trips on the world thread

- **Where:**
  - `Game/Commerce.cs` FollowCreator / UnFollowCreator → `ShowcaseFollow.AddCreator` / `RemoveCreator` (2-3 queries each)
  - `SendAccountStore` → `ShowcaseFollow.Creators` (one query per RequestAccountStore)
- **Failure:** Until today these used an in-memory dictionary. Now every client FollowCreator packet or store open blocks the
  tick on MariaDB. A client spamming FollowCreator / UnFollowCreator (no rate limit) stalls the world tick.
- **Fix:** Do the DB work on a pool thread and post the AddFollowing / RemoveFollowing / AccountStore send back with
  `WebPages`-style `OnWorldThread`. Alternatively, cache each player's creator list in memory at login and write through
  asynchronously.

### 9. LOW: `TicketConsume` gained a trailing u32 without a version, so a mixed deploy fails every login

- **Where:**
  - `LandmarkEmulator.Internal/Login/LoginMessages.cs` (`Write ... .U32(WorldId)`, `Read ... WorldId = r.U32()`)
  - `GatewayClient.cs:117`
- **Failure:** A gateway image built before today talking to today's auth server (or the reverse) produces a short or long
  body. `Read` runs past the end, or leaves a byte unread, and every world login through the login service fails. The
  separate-image test stack (`-test` tags) makes a mixed deploy plausible.
- **Separate observation:** a multi-world gateway passes its primary `ZoneBackEnds.World` while the ticket carries the
  chosen `server.Id`. A direct login to a secondary world through a shared gateway is now refused with no message. That
  is consistent with the gateway attaching new logins to its primary world anyway, but worth a log line.
- **Fix:**
  - Read `WorldId` only when bytes remain (`r.Remaining >= 4 ? r.U32() : 0`), or bump the internal protocol version.
  - Log "ticket for world X used on world Y" at refusal in `ConsumeServerTicketAsync`.

### 10. LOW: one pool task per digest mail

- **Where:** `RemoteCommerceService.cs:298-301` (`Task.Run(() => DeliverDigest(digest))` per `CommerceDigestMail`)
- **Failure:** At the digest hour, or on a world hello with a backlog, `SendPending` can push thousands of mails. That is
  thousands of concurrent `GetCharacterNames` single-row queries against the character DB at once, which can starve the
  connection pool used by the world thread.
- **Fix:** Queue the digests to one consumer, a single `Task` draining a `Channel<CommerceDigestMail>`. Batch the name
  lookups, since `GetCharacterNames` already takes a list.
