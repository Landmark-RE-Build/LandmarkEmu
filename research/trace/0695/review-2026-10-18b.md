## Ranked findings

### 1. MEDIUM: in-process gateway drops the client packets that arrive just before its SOE Disconnect, including the Exit-time preference save

- **Where:**
  - `LandmarkEmulator.WorldServer/Network/ClientSession.cs:47` (`ToZone` → `fromClient` queue)
  - `:51-63` (`OnProcessZonePackets` drains it)
  - `:86` (`OnRemoved() => Zone?.LinkClosed()`)
  - `LandmarkEmulator.Shared/Network/NetworkManager.cs:131-137`: a `Disconnected` session gets no `Update` and goes straight to `pendingRemove`.
- **Failure:**
  - Since `84916ec`, client packets are queued on the UDP thread and handled only in the session's own `Update` → `OnProcessPackets` → `OnProcessZonePackets`.
  - A client's SOE Disconnect (`HandleDisconnect` → `OnDisconnect` on the UDP thread) marks the session `Disconnected`. The next `NetworkManager.Update` therefore never calls `Update` for it, and `OnRemoved` runs `LinkClosed` without draining `fromClient`.
  - So every packet that arrived since the last tick is silently lost. The client sends its last packets and its Disconnect back to back.
  - Concrete case: **Exit Game**. `Game/Preferences.cs` names the Exit path `FUN_142d59850` as a sender of `PreferencePacketClientXml`, right before the process exits. That last chat-window and action-bar save is lost, so the preferences feature (`966dd78`) and the threading fix contradict each other.
  - Ui.Logout is safe: its `CharacterSelectSessionRequest` round trip comes after the preferences.
  - Any other final packet (a last move or chat line, an item action) is lost the same way. The separate gateway is not affected: `GatewayLink` queues `ConnectionClosed` behind the packets on the same work queue.
- **Fix:** drain the queue before the leave. Handlers then run on the world thread, as for live sessions.
  ```csharp
  public override void OnRemoved()
  {
      if (Zone is { } zone)
          while (fromClient.TryDequeue(out var p))
              try { zone.FromClient(p.Channel, p.Data); }
              catch (Exception e) { log.Error(e, $"Client packet from {zone.CharacterName} failed."); }
      Zone?.LinkClosed();
  }
  ```
  `NetworkManager.Shutdown` also calls `OnRemoved`, so shutdown drains too.

### 2. MEDIUM: any player can take admin away from the server owner (name-contest rule)

- **Where:** `LandmarkEmulator.WorldServer/Game/Admin.cs:57-89` (`Contested`, commit `ecd98cc`).
- **Failure:** an entry is "contested" when the other namespace holds the same name, and a contested entry then makes nobody an admin.
  - **Character entry.** The owner lists their character `TestPlayer`. Any player can register a free *account* called `TestPlayer` (`/srp/register`). From then on `AccountExists("TestPlayer")` is true, so the real admin's `byCharacter` match is contested. The owner loses `/admin`, the dev commands and the web admin page, and can't fix it in game.
  - **Account entry.** The same works by creating a *character* named like the owner's account name.
  - The fix closed an escalation, but it opened a cheap denial of service. Recovering needs a config edit and a restart.
- **Fix:**
  - Let entries name their namespace (`account:user`, `character:TestPlayer`), and never consult the other namespace for a prefixed entry.
  - Keep the current contest rule only for unprefixed entries, log the advice to use a prefix, and write the prefixed form into `.env.example` / `docs/admin.md`.
  - Alternative: give a contested *character* entry to the admin when that character's `AccountId` is an account that is also listed.

### 3. MEDIUM: reviewer spend rule does synchronous DB reads on the world tick at every login, and leaks unlock caches

- **Where:**
  - `LandmarkEmulator.WorldServer/Game/Commerce.cs:1114-1123` (`AccountSpent`: `GetCharacters(...).GetAwaiter().GetResult()`, then `Unlocks.ValuesOfAnyone` per alt)
  - `Game/Unlocks.cs:83-88` (`ValuesOfAnyone` → `Load`: a synchronous query, kept in `cache` for good)
  - Called from `MayReview`, which runs in both commerce modes:
    - `Commerce.cs:1185` and `:1277`
    - `WorldChannel/RemoteCommerceService.cs:449`
- **Failure:**
  - The client sends GetProductForReview (0x40) as part of its store start-up at **every login** (docs/protocol.md:1290), and SubmitProductReview on each vote.
  - Each one runs one character-list query and then one full `character_unlock` load per other character of the account, all on the world thread. The loaded unlock sets of alts are never evicted.
  - When an alt spends on another world sharing the character DB, this world's cached value stays stale until restart, so the rule under-counts.
- **Fix:**
  - Compute the account total off the tick with a single query (`SELECT SUM(value) FROM character_unlock WHERE kind = 33 AND characterId IN (…account…)`), then answer through `OnWorldThread`.
  - Or cache per account with a short TTL. Don't put alts into `Unlocks.cache`.

### 4. MEDIUM-LOW: "craft finished at logout" writes into a stale inventory when the character relogs before the old session drops

- **Where:**
  - `LandmarkEmulator.WorldServer/Game/Crafting.cs:283-301` (`Forget` → `session.Inventory.Add(...)`)
  - Reached from `PlayerManager.Enter` → `Leave(old)` (`PlayerManager.cs:54`) on a fast relog or a crash relog.
- **Failure:**
  - The new session built its `Inventory` from the DB in `OnCharacterLogin`, before `Enter`. `Leave(old)` then finishes old's craft into **old's** in-memory inventory.
  - A resource output tops up old's stack and saves the **absolute** count (`m.Count = newCount`). The new session's next save of that stack overwrites it, so the crafted resources are lost.
  - A bag output goes into a slot that old thought was free. The new session can fill the same slot, giving two rows in one slot until `RehomeMisplacedItems` at the next login. The item is also invisible in this session.
  - The same applies to `RemoteMail` escrow give-backs that land on old (pre-existing).
- **Fix:** give the output to the replacement session when there is one. At `Leave(old)` time the new session is not in `players` yet, so `FindByGuid` can't find it. Look it up in `WorldSession.ZoneSessions` (`s != session && s.PlayerGuid == session.PlayerGuid && !s.Disconnected`) and use `GiveItem` there. Without a replacement, keep the current behaviour.

### 5. LOW-MEDIUM: Founder's Chest runs one DB query per founder item on the world tick, and clicks are not rate-limited

- **Where:** `LandmarkEmulator.WorldServer/Game/Entitlements.cs:235`. `HasMailAttachment` per item → `Mail.HasAttachment` reads and parses every mail of the recipient. In remote mode it calls `RemoteMail.HasAttachment`.
- **Failure:** every click on the Spire's Founder's Chest runs N synchronous `mail` table scans on the tick, N being the non-trade items of the founder package. Spam-clicking stalls the world for everyone.
- **Fix:** load the recipient's attachment kinds once (one query → `HashSet<uint>`). Add a per-player cooldown (for example 5 s) on `RestoreFounderItems`.

### 6. LOW: bag-placement build mode is closed from a pool thread

- **Where:** `LandmarkEmulator.WorldServer/Game/BuildModeHolster.cs:126` (`Task.Delay(CloseDelayMs).ContinueWith(_ => CloseAfterPlacement(session))`).
- **Failure:** the same pattern that `23b648c` / `3470abe` removed from travel casts and Repair Bots ("bughunt-combat B7"). `CloseAfterPlacement` locks `Props.sync` and enqueues Lua on a pool thread, with no `Disconnected` check. It is safe today only because everything it touches is locked or concurrent.
- **Fix:** queue it on the tick with a due list, as `Abilities.Later` / `Consumables.UpdateRepairBots` do, and skip disconnected sessions.

### 7. LOW: the bag placement's close can close the player's own build mode

- **Where:** `BuildModeHolster.cs:88-104` and `:131-142`.
- **Failure:**
  - `OpenForPlacement` adds the player to `openedByPlacement` before knowing whether the client really opened build mode. `OpenCode` is guarded by `Voxel.AllowBuildingMode()`, so the client may do nothing.
  - If the player then presses Tab themselves, `BuildMode(true)` leaves `openedByPlacement` set. When the placement ends, `CloseAfterPlacement` runs `CloseCode` and closes the build mode the player opened.
- **Fix:** mark the session "pending open" and move it into `openedByPlacement` only when `BuildMode(true)` arrives within about 2 s of `OpenCode`. Any other `BuildMode(true)` clears the pending mark.

### 8. LOW (test before relying on it): a value change hidden in a rename commit, AddLightweightPc `ProfileId`

- **Where:** `LandmarkEmulator.WorldServer/Network/WorldSession.cs:426` (`ProfileId = profileId`, added in `4fbea31` "name every field…").
- **Failure:**
  - Every remote player is now spawned on other clients with their current profile id. The client stores it at entity +0x1474 and looks profile definitions up by it.
  - Before, it was always 0. The commit claims no client test.
  - If a profile row changes a remote actor's animation set or stance, other players' looks change for everyone.
- **Fix:**
  - Test it with two clients: walk, swim, combat stance and build mode.
  - Or put it behind a setting until then.
  - Or move it out of the rename commit's scope.

### 12. LOW (data): the Unlocks kind for store spend moved from 32 to 33 in a merge

- **Where:** `Game/Unlocks.cs:56` (merge `96ef517`).

### 13. LOW: TemplateInstances — the in-memory row's Id is set by EF on a save thread

- **Where:** `LandmarkEmulator.WorldServer/Game/TemplateInstances.cs:69-76` (Record), `:112-123` (Forget by `r.Id`).
- **Failure:**
  - The same `row` object is added to the list and passed to the asynchronous `SaveWorld`. EF writes its identity `Id` on the save thread.
  - A `Forget` before the save finishes deletes `Id = 0`, which does nothing. This happens with `psinstances clear` right after a placement, or when a site is removed right after.
  - The database keeps the row, and it is loaded again at the next start. It is dropped as stale only when its site is gone.
- **Fix:** save a copy and assign the generated `Id` back on the world thread. Or delete by `(ZoneId, SiteGuid, TemplateGuid, PlacedAt)`.

### 14. LOW: with overflow expiry on, overflow never stacks, so the 500-slot tab can drop items

- **Where:** `Game/Inventory/Inventory.cs:369` (`OverflowExpiryHours == 0` in `AddOverflow`), cap at `:39` (500 slots).
- **Failure:**
  - With the default 24 h expiry, every arrival takes a new overflow slot so that each keeps its own timer.
  - A player with a full bag who loots or gathers non-resource items for a while fills 500 slots, after which items are dropped. The only trace is the log line "bag and overflow are full; dropped".
- **Fix:** top up an overflow stack whose `ExpiresAt` is in the same minute (or keep the earliest end; the client shows a single countdown anyway). Or tell the player when something is dropped.

### 15. LOW (parser/tests only): character-select friend count bound too tight

- **Where:** `LandmarkEmulator.AuthServer/Network/Message/Model/CharacterSelectInfoReply.cs:244` (`BytesRemaining / 33u`).
- **Failure:** the smallest `Friend` record is 29 bytes: u32, three empty strings, u64, bool, empty string. Three or more offline friends with names of three characters or fewer make `Read` throw "friends refused". This only affects the capture parser and the tests; the server writes, it doesn't read this.
- **Fix:** use `29u`.

  - The auth `CharacterSelectFriends` / `SocialAddress`, commerce `PlayerStudioReviewsPerDay` / `StaffReview`, gateway `EncryptionKey` and world channel `LoginInternalAddress` are wired. `ITEM_AUTO_RESUPPLY` (new HEAD commits) is wired in all four places.
- **Renamed packet models.** Old and new read/write call sequences match byte for byte for:
  - Sky → `ContinentDefinition`: u64 → f64 `VoxelSize` / `OceanHeight` and u32 → f32 keep the same bits.
  - `SendZoneDetails`, where the old `Trailing` byte is now `IsNewbieZone`, the same length.
  - `ClientBeginZoning`, where the old slot names were offset by four. The old `ZoneNameId = WorldOf(zone)` and `Unknown8 = zone` land on the new `WorldId` / `ZoneId`, so no unintended change.
  - `ClientGameSettings`: the live bytes are unchanged.
  - `AreaDefinition*`, `InventoryItem`, `Objective`, `Mount` and `Achievement`. Achievement's `VisibilityType = 4` default is never written by the server.

  - `ArtData` / ArtTints.json: the tests pin the 735,806-byte body by SHA-256.
- **Opcode codec.** `PadLeft(4)` changes only one-byte values; `DebugDrawBase` 0x0001 is the only one, and `PreferencePacket = 0x300` is unchanged. The three enum fixes (`ToolActivate` / `ToolUndoStackChange` / `AddProfileAbilitySetApl`) are unused by the code or correct.

  - The input stream starting at 0 and the parse loop are correct.
  - The length guards on short datagrams and protocol packets are correct.
